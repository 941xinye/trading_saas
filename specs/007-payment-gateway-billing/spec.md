# Feature Specification: P9 支付网关 + 计费 UI

**Feature Branch**: `007-payment-gateway-billing`

**Created**: 2026-10-20

**Status**: Draft

**Input**: User description: "P9 支付网关 + 计费 UI。为数字货币交易 SaaS 平台接入支付收单与计费界面，完成商业化闭环（依赖 P3 多租户计费）。合规前置结论：基线=BTCPay Server 自托管 USDT 收单 + 手工续费；备选 NOWPayments/BitPay/Binance Pay；Stripe 申报作远期并行线；支付宝/微信排除。范围：①支付集成（BTCPay 首发，通道抽象层预留多通道）②Filament 计费页（套餐升级/Invoice/用量看板）③订阅激活接线（支付成功→激活/续期→配额刷新）④续费失败流转（到期前提醒→手工续付→P3 past_due→grace→suspended）⑤webhook 验签 + 同 ref 幂等。验证目标：完整一笔闭环；同 ref 重放 3 次只激活一次；续费失败走 P3 流程。关键风险：回调幂等、汇率/税额、通道合规、金额精度（bcmath）、租户隔离。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 套餐购买支付闭环 (Priority: P1)

租户（免费版用户）在计费页选择升级到 pro 套餐，系统生成一笔 USDT 支付单（含收款地址与金额），租户用自己的钱包转账支付；平台确认到账后，该租户的订阅自动激活为 pro，配额立即按新套餐刷新，租户立即可用 pro 级策略（futures_grid / custom_dsl）。

**Why this priority**: 这是平台第一笔收入的唯一通路；没有它，P3 计费系统空转、平台无法商业化。

**Independent Test**: 用测试通道创建一笔 pro 升级支付单，模拟支付到账回调，验证订阅状态从 free→active(pro)、配额刷新、且全流程无需人工介入。单独交付即构成可收费 MVP。

**Acceptance Scenarios**:

1. **Given** free 租户已登录计费页, **When** 选择 pro 套餐并确认升级, **Then** 系统生成一笔待支付单，展示 USDT 金额、收款地址与支付倒计时
2. **Given** 存在一笔待支付单, **When** 支付通道确认足额到账, **Then** 订阅激活为目标套餐、配额立即刷新、支付单状态变为已确认
3. **Given** 支付单已生成但未支付, **When** 超过支付有效期, **Then** 支付单过期失效，租户可重新发起升级生成新支付单

---

### User Story 2 - Webhook 安全与幂等 (Priority: P2)

支付通道通过 webhook 通知平台支付结果。平台必须验证 webhook 签名真实性（伪造通知一律拒绝并留审计），且同一笔支付的重复通知（网络重试/人工重放/恶意重放）不会导致重复激活、重复续期或重复记账。

**Why this priority**: 资金安全红线——伪造回调=白送套餐，重复回调=重复续期；这是支付系统被攻击的主要面。独立成故事是因为可脱离 UI 单独验证（对应 docs/p9-btcpay-poc-plan.md 阶段 B）。

**Independent Test**: 对同一笔支付单 ref 连续重放 3 次相同 webhook，断言订阅激活记录恰好 1 条、配额仅刷新 1 次；用错误签名重放，断言 100% 拒绝且零状态变更。

**Acceptance Scenarios**:

1. **Given** 一笔已确认的支付单, **When** 同一 ref 的 webhook 再次到达（共重放 3 次）, **Then** 后续重放全部幂等跳过，激活记录恰好 1 条，无重复续期
2. **Given** 任意支付单, **When** 收到签名无效的 webhook, **Then** 请求被拒绝、支付单状态不变、事件落审计（含原始载荷）
3. **Given** 同一支付单, **When** webhook 乱序到达（先 confirmed 后 processing）, **Then** 状态机只向终态前进，不回退

---

### User Story 3 - 订阅续费与失败流转 (Priority: P2)

订阅到期前，系统按节奏提醒租户续费；租户手工发起续费支付（同 US1 链路）后续期成功。若到期未续费，订阅沿 P3 既有状态机流转：past_due → 宽限期 → suspended，期间配额按状态收缩；宽限期内补缴成功则恢复。

**Why this priority**: push 模式无代扣，续费只能靠「提醒→手工续付」；续费留存直接决定收入持续性。复用 P3 状态机所以与 US1 并列 P2。

**Independent Test**: 构造一个即将到期的订阅，验证提醒按节奏发出；不续费则观察 past_due→grace→suspended 完整时间线；宽限期内支付续费单则恢复 active 且配额复原。

**Acceptance Scenarios**:

1. **Given** 订阅将在 N 天后到期, **When** 到达提醒时点（到期前 7/3/1 天）, **Then** 租户收到续费提醒（通知中心），提醒含一键续费入口
2. **Given** 订阅已到期未续费, **When** 超过宽限期, **Then** 订阅转 suspended，策略实例按 P3 既有语义停止，配额收缩
3. **Given** 订阅处于宽限期, **When** 租户完成续费支付, **Then** 订阅恢复 active、周期顺延、配额刷新，不产生双重计费

---

### User Story 4 - Filament 计费页 (Priority: P3)

租户在 Admin 面板的计费页完成全部自助操作：查看当前套餐与配额用量看板、发起套餐升级、查看历史支付单列表与每笔支付状态、找到续费入口。

**Why this priority**: 自助化运营的前界面，但 US1–US3 均可用命令行/接口先行验证；界面层最后交付不阻塞收入验证。

**Independent Test**: 以两个不同租户登录，各自完成升级发起与支付单查询，验证数据互不可见；用量看板数字与 P3 计量口径一致。

**Acceptance Scenarios**:

1. **Given** 租户登录计费页, **When** 查看用量看板, **Then** 展示当前套餐、周期起止、各计量事件已用量/上限（与 P3 计量口径一致）
2. **Given** 租户有多笔历史支付单, **When** 打开支付单列表, **Then** 按时间倒序展示金额/状态/创建时间，且仅可见本租户数据
3. **Given** 租户已有一笔待支付单, **When** 再次点击升级, **Then** 引导至既有待支付单（或明确提示先完成/取消），不堆叠多笔待支付单

---

### Edge Cases

- **不足额支付（partially paid）**：支付单不激活，状态标记为部分支付，差额处理见澄清 Q2
- **超额支付**：超过应付金额的部分不退款不记账，默认人工线下处理
- **过期后到账（paid_late）**：支付单已过期后资金才到账，不自动激活，状态标记待人工处理
- **确认数未达标**：链上转账已广播但未达确认数要求时，支付单保持「支付中」，不激活
- **重复发起升级**：同一租户同一目标套餐同时最多存在一笔待支付单；新发起作废旧单
- **通道不可用**：创建支付单时通道异常，返回明确错误且不产生半状态支付单
- **webhook 洪流/恶意重放**：验签失败请求全部拒绝，且单 ref 处理有并发防重（同 ref 并行到达只处理一次）
- **升级与熔断/暂停状态叠加**：订阅 suspended 期间发起新购买，支付成功后直接激活并恢复实例（按 P3 恢复语义）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供支付通道抽象层，首发接入 BTCPay Server 自托管通道；新增通道（NOWPayments/BitPay 等备选）只允许纯增量接入，不改动既有通道与订阅接线代码
- **FR-002**: 租户发起套餐升级/续费时，系统 MUST 生成支付单：含租户、目标套餐、USDT 金额（bcmath 精度）、收款信息、过期时间与唯一 ref；同一租户同一目标套餐同时最多一笔待支付单
- **FR-003**: 系统 MUST 追踪支付单状态机：待支付 →（支付中）→ 已确认 / 过期 / 部分支付 / 待人工；状态只向终态前进，乱序通知不回退
- **FR-004**: 系统 MUST 接收支付通道 webhook 并验签；验签失败的请求 MUST 拒绝、零状态变更、落审计（含原始载荷与失败原因）
- **FR-005**: 系统 MUST 以支付单 ref 为幂等键：同一 ref 的 webhook 无论到达多少次，订阅激活/续期与配额刷新 MUST 只执行一次；同 ref 并发到达 MUST 防重
- **FR-006**: 支付确认后，系统 MUST 原子完成订阅接线：订阅激活/续期（复用 P3 SubscriptionService）+ 配额刷新（复用 P3 计量口径）+ 审计落库；任一步失败 MUST 可重试且不产生半激活状态
- **FR-007**: 系统 MUST 在订阅到期前按 7/3/1 天节奏向租户发送续费提醒（复用既有通知域），提醒含续费入口
- **FR-008**: 到期未续费的订阅 MUST 沿 P3 既有状态机流转（past_due → 宽限期 → suspended），宽限期时长沿用 BILLING_PAST_DUE_GRACE_DAYS 配置；宽限期内续费成功 MUST 恢复 active 且周期顺延
- **FR-009**: 系统 MUST 提供 Filament 计费页：当前套餐与用量看板（与 P3 计量口径一致）、套餐升级入口、支付单列表（时间倒序：金额/状态/创建时间）、续费入口
- **FR-010**: 支付单、订阅操作、用量数据 MUST 严格租户隔离；跨租户访问 MUST 拒绝
- **FR-011**: 所有金额计算与比较 MUST 使用 bcmath 字符串精度，禁止浮点参与
- **FR-012**: 支付单 MUST 有支付有效期；过期未支付自动失效，租户可重新发起；过期后到账不自动激活，转待人工
- **FR-013**: 不足额支付 MUST 不激活订阅，支付单标记部分支付状态（差额处理见澄清 Q2）
- **FR-014**: 系统 MUST 不提供自动退款能力；退款为人工线下流程，平台侧仅需支持支付单人工标记

### Key Entities *(include if feature involves data)*

- **PaymentInvoice（支付单）**：一笔套餐购买/续费收款单据。关键属性：唯一 ref（幂等键）、租户、目标套餐、USDT 金额、收款信息、状态、过期时间、通道标识、确认时间
- **PaymentChannel（支付通道）**：收单通道抽象。首发实现为 BTCPay Server 自托管；预留 NOWPayments/BitPay/Binance Pay；通道间无共享状态
- **WebhookEvent（支付通知事件）**：一次 webhook 接收记录。关键属性：ref、验签结果、原始载荷、处理结果（已处理/幂等跳过/拒绝）、接收时间；用于审计与重放排查
- **复用既有实体**：Subscription / Plan / Tenant / meter_events（P3，不新增字段语义，只新增激活触发源）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一笔真实/模拟支付从「发起升级」到「订阅激活且配额可用」全程 ≤ 10 分钟（含链上确认等待），其中平台侧处理（确认到账→激活→配额刷新）≤ 30 秒
- **SC-002**: 同一 ref 的 webhook 连续重放 3 次，激活记录恰好 1 条、配额恰好刷新 1 次、支付单状态无异常迁移——0 例外
- **SC-003**: 签名无效的 webhook 100% 被拒绝且零状态变更，审计记录 100% 留存
- **SC-004**: 到期不续费场景可完整重现「提醒 → past_due → 宽限期 → suspended →（补缴）恢复」时间线，各状态转换时点与 P3 配置一致，误差 ≤ 1 个调度周期
- **SC-005**: 租户在计费页从「点击升级」到「看到收款信息」≤ 3 步操作、≤ 1 分钟
- **SC-006**: 双租户并发各完成一笔支付，双方支付单/订阅/用量数据零串扰（跨租户访问 100% 拒绝）

## Assumptions

- 套餐以 USDT 计价（展示上 1 USDT ≈ 1 USD 锚定），首发不接法币与汇率换算；税额/合规申报为平台运营线下职责，不进本功能
- 计费周期（月/年）与价格沿用 plans.php 既有定义（P3），本功能不引入新套餐
- 无账户余额/预充值概念：每次购买/续费生成独立支付单，逐笔支付
- 平台支付单是收款凭证，不含税务发票（invoice 税务语义不进范围）
- 不提供自动退款；加密支付 push 模式无法原路退回，退款人工线下处理
- 链上确认数要求由通道配置决定（默认 BTCPay 达到配置确认数后通知 confirmed）
- Stripe 申报为远期并行线，不进本 spec 范围；支付宝/微信已合规排除
- BTCPay Server 节点部署由运营侧完成（docs/p9-btcpay-poc-plan.md 阶段 A），本功能从「通道可达」起步

## Clarifications Resolved
