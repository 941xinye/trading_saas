# Feature Specification: P10 回测引擎 + 绩效分析

**Feature Branch**: `008-backtest-engine`

**Created**: 2026-10-20

**Status**: Draft

**Input**: User description: "P10 回测引擎 + 绩效分析：基于 ClickHouse 历史 K 线（P8 HistoricalQuery）分页回放驱动 BarAggregator，对既有已实装策略（spot_grid / spot_dca / custom_dsl / futures_grid）在历史数据上产生决策序列并模拟撮合（手续费/滑点为可配置假设，显式标注），输出净值曲线与绩效指标（Sharpe、最大回撤、胜率、盈亏比、收益率），回测任务与结果持久化，提供 Filament 绩效页查看回测报告。核心约束：回测与实跑共用同一策略解释器与指标计算器（复用 spec 006 HistoricalPreviewService 范式），保证语义一致；验收目标：一条 DSL 策略回测 1 年 5m K 线 < 30s、与实跑同策略净值曲线误差 < 1%（扣除撮合假设差异）。范围边界：README P10 行所列「与 P4 风控参数自动调优建议」留作后续迭代不在本期。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 对策略发起回测并获得绩效报告 (Priority: P1)

租户选择自己的一条策略实例（或一段 DSL 策略配置）与历史回测区间，发起回测；回测完成后得到一份绩效报告：净值曲线（时间序列）、总收益率、年化收益率、Sharpe 比率、最大回撤、胜率、盈亏比、交易次数。报告基于历史 K 线回放产生，全程不触碰任何真实交易所账户。

**Why this priority**: 这是 P10 的核心价值——用户在投入真实资金前能用历史数据验证策略表现；没有报告产出，其余故事均无意义。

**Independent Test**: 对一个 spot_grid 实例发起 30 天回测，断言产出报告包含净值曲线与全部核心指标、交易次数与网格决策数一致、且全程交易所调用次数为 0。单独交付即构成可用 MVP。

**Acceptance Scenarios**:

1. **Given** 租户有一条已配置的 spot_grid 策略实例, **When** 选择近 30 天区间发起回测, **Then** 回测完成并产出含净值曲线与核心指标的完整报告
2. **Given** 任一回测任务, **When** 回测执行期间, **Then** 不产生任何真实下单、不改变任何实盘/模拟盘实例状态（交易所零调用）
3. **Given** 回测已产出报告, **When** 指标区域查看, **Then** 总收益率/年化/Sharpe/最大回撤/胜率/盈亏比/交易次数全部可见且数值口径明确（bcmath 精度，无浮点误差展示）

---

### User Story 2 - 回测与实跑语义一致性 (Priority: P1)

回测产生的决策序列必须与实跑引擎同源：同一策略解释器、同一指标计算器（复用 spec 006 HistoricalPreviewService 范式），禁止为回测另写一套决策逻辑。在同一策略、同参数、同一批历史 K 线下，回测净值曲线与实跑记录的误差 < 1%（差异仅允许来自滑点/手续费等撮合假设）。

**Why this priority**: 语义一致性是回测报告可信的前提——若回测与实跑行为分叉，报告就是误导。这是本 spec 区别于 spec 006「预览」的核心增量（预览只看信号序列，回测要资金曲线对得上实跑）。

**Independent Test**: 取一段已实跑产生过成交记录的 testnet 实例历史，用相同参数与区间回测，断言决策序列（bar/side/qty 语义）一致、净值曲线误差 < 1%（扣除撮合假设差异后可解释）。

**Acceptance Scenarios**:

1. **Given** 同一策略同参数的历史区间, **When** 分别回测与回放实跑记录, **Then** 开平仓决策序列一致（方向/时点），金额差异完全可归因于撮合假设
2. **Given** 同一 DSL 脚本, **When** 分别在预览（spec 006）与回测（本期）中运行, **Then** 两者信号序列一致（复用同一解释器的直接推论）
3. **Given** 回测引擎代码, **When** 引入任何绕过共用解释器的独立决策路径, **Then** 一致性守护测试失败（架构级守护，非一次性验证）

---

### User Story 3 - 回测任务持久化与异步执行 (Priority: P2)

回测在独立队列异步执行（不阻塞行情/交易链路），任务有完整生命周期（pending → running → completed / failed）；报告与净值曲线持久化，之后任意次查看均直接读取已存结果，不重算；同租户同实例同参数的重复回测产生新报告（不覆盖历史报告）。

**Why this priority**: 1 年数据回测是重负载操作，同步执行会拖垮请求；报告重看不重算决定产品可用性。P1 故事可用同步内存路径先行验证，持久化/异步是工程化必需但不阻塞 MVP。

**Independent Test**: 发起一次回测后轮询任务状态直至 completed；再次打开报告断言加载耗时可忽略（无重算）；构造一个必然失败的任务（如区间内无数据）断言状态为 failed 且含可读错误信息。

**Acceptance Scenarios**:

1. **Given** 一次已完成的回测, **When** 租户再次查看该报告, **Then** 直接读取持久化结果（秒级），不触发重新计算
2. **Given** 回测区间内历史 K 线存在缺失, **When** 回测完成, **Then** 报告显式标注数据覆盖率/缺失区间，而非静默跳过
3. **Given** 回测执行中, **When** 同租户发起第二笔回测, **Then** 依据租户并发上限或排队（不超载执行节点）

---

### User Story 4 - 撮合假设可配置并显式标注 (Priority: P2)

回测的撮合模型基于 bar 级假设：以 K 线收盘价成交，手续费率与滑点（bps）为可配置参数（有合理默认值）；每份报告显式标注所用假设，使「回测 ≠ 未来收益」的差异来源透明可查。报告注明未建模的现实因素（部分成交、盘口深度、资金费率等）。

**Why this priority**: 撮合假设直接决定回测可信度边界；不标注假设的报告会诱导用户过度信任。与 US1 同为报告产出的一部分，但不阻塞「有报告」本身，故列 P2。

**Independent Test**: 以两组不同手续费率回测同一策略同区间，断言报告收益差异与费率假设一致；断言报告页可见假设参数区（费率/滑点/初始资金/撮合口径）。

**Acceptance Scenarios**:

1. **Given** 默认撮合参数发起回测, **When** 查看报告, **Then** 假设区显示手续费率、滑点、初始资金、撮合口径（bar 收盘价）
2. **Given** 手续费率调高一倍, **When** 重新回测同一策略同区间, **Then** 报告总收益下降且交易手续费总额相应上升
3. **Given** futures_grid 策略回测, **When** 历史资金费率数据不可得, **Then** 报告标注「未含资金费率影响」的明确免责说明

---

### User Story 5 - Filament 绩效页 (Priority: P3)

租户在 Admin 面板的绩效页完成自助操作：选择实例与区间发起回测、查看进行中任务进度、打开历史回测报告列表、查看单份报告详情（净值曲线图 + 指标卡 + 假设区 + 交易明细）。

**Why this priority**: 自助化界面，但 US1–US4 均可经命令行/接口先行验证（仓库既有 POC 范式），UI 最后交付不阻塞核心能力。

**Independent Test**: 双租户各自发起回测并查看报告，断言互不可见对方任何回测数据（租户隔离）；报告页净值曲线与指标数值一致。

**Acceptance Scenarios**:

1. **Given** 租户登录绩效页, **When** 选择实例与区间提交回测, **Then** 任务创建成功并展示进行中状态
2. **Given** 有多份历史报告, **When** 打开报告列表, **Then** 按时间倒序展示策略/区间/收益率/状态，仅含本租户数据
3. **Given** 一份已完成报告, **When** 打开详情, **Then** 净值曲线可视化、指标卡、假设区、交易明细四区域齐全

---

### Edge Cases

- **历史数据不足**：实例创建时间晚于回测起点、或区间内 K 线覆盖率过低（如 < 80%）时，回测产出带数据覆盖率标注的报告，不静默截断也不直接失败（阈值在 plan 阶段定）
- **futures_grid 资金费率**：永续合约回测缺历史资金费率数据源时，标注未含该影响；有数据源则纳入（plan 阶段评估数据可得性）
- **回测期间策略配置变更**：回测基于发起时刻的参数快照执行，期间实例参数/DSL 编辑不影响进行中的回测
- **DSL 策略被删除**：回测完成前 DSL 被删，进行中的回测不受影响（参数快照已含脚本内容），报告可正常产出
- **超长区间/数据量上限**：回测区间超过上限（plan 阶段定，初值 1 年）时明确拒绝并提示，而非隐性 OOM
- **并发冲突**：同一实例同时只允许一个进行中的回测任务（重复发起给出明确提示），不同实例可并行
- **零交易策略**：回测区间内策略无任何决策，报告正常产出（净值恒为初始资金、交易次数 0、胜率等指标标注「无交易」而非除零错误）
- **回测中断**：队列 worker 崩溃时任务标记 failed（不悬挂 running），可重新发起

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持对四种已实装策略（spot_grid / spot_dca / custom_dsl / futures_grid）发起历史回测；未在 `strategy.implemented` 白名单的策略类型一律拒绝
- **FR-002**: 回测数据必须经历史 K 线查询层（P8 `HistoricalQuery` 抽象，冷热分层自动路由）读取，按策略所需周期经 BarAggregator 同口径聚合；MySQL/CH 不可达时明确报错，不降级到其他数据源
- **FR-003**: 回测必须与实跑共用同一策略解释器与指标计算器；**禁止**在回测路径内复制或重新实现任何决策逻辑（架构级约束，测试守护）
- **FR-004**: 回测执行全程必须零真实交易所调用（行情、下单、账户接口均不得触达）
- **FR-005**: 撮合假设（手续费率、滑点 bps、初始资金、bar 收盘价成交口径）必须可配置且有默认值；每份报告必须显式展示全部假设
- **FR-006**: 回测输出必须包含：净值曲线时间序列、总收益率、年化收益率、Sharpe 比率、最大回撤、胜率、盈亏比、交易次数、手续费总额；全部金额/数量计算用 bcmath 字符串精度，绩效比率计算口径在报告中注明
- **FR-007**: 回测任务必须有持久化生命周期（pending → running → completed / failed），失败时留存可读错误信息
- **FR-008**: 回测报告（指标 + 净值曲线 + 交易明细 + 假设快照）必须持久化；历史报告重复查看不重算
- **FR-009**: 同一实例同时只允许一个进行中的回测任务；每租户并发回测数有上限（具体值 plan 阶段定，按套餐差异化）
- **FR-010**: 回测必须按租户隔离：只能回测本租户实例/DSL，报告仅本租户可见
- **FR-011**: 回测不消耗既有 AI/下单配额，不计入 TwoPhaseMeter 计量事件（商业化策略如变化在后续 spec 调整）
- **FR-012**: 回测区间与周期由用户选择；区间上限与 K 线覆盖率下限有明确配置，超限拒绝并提示
- **FR-013**: 回测报告必须标注数据覆盖率与已知未建模因素（部分成交、盘口深度、资金费率可用性等）
- **FR-014**: 提供命令行入口（POC/运维范式与既有 `poc:verify-*` 一致）与 Filament 绩效页两个入口，能力对等（页面为自助主入口）

### Key Entities *(include if feature involves data)*

- **回测任务（Backtest Run）**：一次回测执行的记录——发起租户、目标策略实例与参数快照（含 DSL 脚本内容）、回测区间与周期、撮合假设快照、生命周期状态、错误信息
- **回测报告（Backtest Report）**：任务的产出——绩效指标集（收益率/年化/Sharpe/最大回撤/胜率/盈亏比/交易次数/手续费总额）、净值曲线时间序列、逐笔模拟交易明细、数据覆盖率标注
- **模拟交易（Simulated Trade）**：回测产生的一笔模拟成交——方向、模拟成交价（含滑点）、数量、手续费、关联 bar 时点；与实盘订单表无关（不落 strategy_orders）
- **撮合假设（Matching Assumptions）**：费率/滑点/初始资金/成交口径的参数集合，随任务快照持久化，保证报告可复现

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一条 DSL 策略对 1 年 5m K 线（约 105,000 根）完成回测并产出报告，总耗时 < 30 秒
- **SC-002**: 同一策略同参数下，回测净值曲线与实跑记录对比误差 < 1%（扣除滑点/手续费假设差异后）；决策序列（方向/时点）一致率 100%
- **SC-003**: 已完成报告的再次查看加载时间 < 2 秒（零重算）
- **SC-004**: 租户从发起到看到报告（30 天区间）全流程 ≤ 2 分钟
- **SC-005**: 全部回测场景实测中交易所 API 调用次数为 0（含行情接口）
- **SC-006**: 双租户并发回测，报告、任务、指标零串扰（租户隔离验证）

## Assumptions

- **撮合口径**：bar 级模拟（K 线收盘价成交 + 固定滑点 bps），不做盘口深度/部分成交建模；该口径与 spec 006 预览一脉相承，为已知边界而非缺陷，报告中显式标注
- **默认参数**：初始资金默认 1000 USDT；手续费率默认参考 Binance 现货 taker 费率（0.1%）；滑点默认 5 bps；回测区间默认近 90 天、上限 1 年（均可配置，plan 阶段定具体配置键）
- **绩效口径**：Sharpe 按所选周期无风险利率默认 0 计算；年化按 365 天折算；口径写入报告，不引入多口径切换
- **数据可得性**：回测依赖 P8 归档与 MySQL 热数据衔接良好（applied 水位路由已交付）；CH 节点未部署时，热数据覆盖的区间仍可回测（ HistoricalQuery 冷热路由的既有语义）
- **计费边界**：回测不计配额（FR-011）是商业化初始决策；若未来回测成为高成本服务需计量，另立 spec
- **范围边界**：「与 P4 风控参数自动调优建议」（README P10 行）不在本期；多策略批量回测、参数网格寻优不在本期
- **依赖关系**：依赖 P1（BarAggregator/策略域）、P7（DSL 解释器，spec 006）、P8（HistoricalQuery，spec 004）；对 testnet 实跑数据的一致性验收（SC-002）依赖既有 testnet 成交记录样本
