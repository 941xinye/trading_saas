# Feature Specification: ClickHouse 历史数据归档（P8）

**Feature Branch**: `004-clickhouse-historical-archive`

**Created**: 2026-10-18

**Status**: Draft

**Input**: User description: "P8 ClickHouse 历史数据归档：kline_bars / signals / strategy_orders / liquidation_events 冷热分层归档到 ClickHouse，查询层抽象 HistoricalQuery，为 P10 回测与 P7 回测预览提供统一历史查询能力"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 冷数据归档，主库瘦身，业务零感知 (Priority: P1)

平台运营者发现四类持续增长的时序表（K 线、信号、策略订单、爆仓事件）让主库备份越来越慢、热查询越来越钝。运营者启动一次归档：超过保留期的历史行被搬入专门的时序历史存储，主库只保留近期热数据。归档运行期间，正在跑的网格策略、信号分析、下单链路完全无感——没有一条请求被阻塞、没有一个订单因迁移失败。

**Why this priority**: 数据持续增长是每天都在恶化的既成事实，归档越晚迁移窗口越大、历史校验越难（2026-10-18 路线决策：P8 先于 P7 的核心理由）。且这是后续两个用户故事的前提——没有归档就没有"冷热分层查询"可言。

**Independent Test**: 造一批超过保留期的历史行 + 持续的实时写入，执行归档，验证：超期行进入历史存储、主库行数下降、归档期间实时写入与读取零失败。

**Acceptance Scenarios**:

1. **Given** 主库存在超过保留期的历史行且归档服务可用，**When** 执行归档，**Then** 超期行出现在历史存储中、主库对应行被移除（移除前完成校验）、行数账目对平。
2. **Given** 归档正在运行，**When** 策略实例持续产生新订单与新 K 线写入，**Then** 所有写入与读取正常完成，无阻塞、无失败、无脏数据。
3. **Given** 归档在批次中途被强制中断（进程被杀），**When** 重新执行归档，**Then** 不产生重复行、不丢失行，从断点续跑完成。

---

### User Story 2 - 统一历史查询入口，调用方不感知冷热 (Priority: P1)

策略开发者要为回测（P10）与 DSL 回测预览（P7）读取历史 K 线：查询"某交易对过去一年的 5m K 线"。数据一部分还在主库（近期）、一部分已归档（早期），但调用方只面对一个查询入口，拿到的结果是一条完整、有序、不重不漏的时间序列——系统内部自动路由冷热两层并合并。

**Why this priority**: 这是 P8 立项的最终目的——P10 回测与 P7 回测预览都依赖这个统一入口；没有它，归档只是搬数据，业务用不上。

**Independent Test**: 归档部分历史 K 线后，通过统一入口查询跨越归档边界的时间范围，验证返回结果 = 纯主库时代的完整结果（行数一致、顺序正确、边界不丢不重）。

**Acceptance Scenarios**:

1. **Given** 某交易对 1 年的 5m K 线中最近 90 天在主库、其余已归档，**When** 查询整年范围，**Then** 返回完整有序序列，与归档前基线行数一致，无重复行。
2. **Given** 查询范围完全落在主库热数据内，**When** 查询，**Then** 结果正确且不因归档层引入额外失败风险。
3. **Given** 查询范围完全落在已归档冷数据内，**When** 查询，**Then** 结果从历史存储正确返回。

---

### User Story 3 - 租户隔离贯穿历史层 (Priority: P1)

租户 A 的用户查询自己的历史信号与订单，结果完整；任何试图通过历史查询入口读取租户 B 归档数据的请求都被拒绝。归档不能成为行级隔离的旁路。

**Why this priority**: 信号与订单是租户敏感数据（P1-P5 全部建立在行级隔离之上），归档若破坏隔离等于开了一个跨租户泄露口——资金与隐私风险，必须与归档本体同优先级交付。

**Independent Test**: 双租户各造历史数据并归档，以租户 A 身份查询历史层，断言仅返回 A 的行；无租户上下文的越权查询被拒。

**Acceptance Scenarios**:

1. **Given** 租户 A 与租户 B 的历史信号均已归档，**When** 以 A 的身份查询历史信号，**Then** 仅返回 A 的行，B 的行在任何过滤条件下不可见。
2. **Given** 带租户上下文的历史查询，**When** 强行指定他人租户标识作为过滤条件，**Then** 请求被拒绝或过滤条件被强制覆盖为自身租户。

---

### User Story 4 - 历史存储故障不伤热链路 (Priority: P2)

历史存储部署故障或维护下线。行情接入、K 线聚合、策略调度、下单、信号、计费一切照常——历史查询入口返回明确的"历史层暂不可用"错误，而不是让整个应用跟着挂。

**Why this priority**: 历史存储是新增的旁路依赖，绝不能变成主链路的单点故障；但热链路保护的价值在归档落地后才显现，故排在归档与查询之后。

**Independent Test**: 归档运行中人工断开历史存储，验证热链路全部操作正常、归档任务失败但不污染主库数据、恢复后归档可续跑。

**Acceptance Scenarios**:

1. **Given** 归档任务运行中历史存储断连，**When** 任务重试，**Then** 主库数据未被半途修改产生脏状态，任务报错清晰，恢复连接后续跑成功。
2. **Given** 历史存储整体不可用，**When** 用户进行下单/信号/网格调度等热操作，**Then** 全部正常；仅历史查询返回明确降级错误。

---

### User Story 5 - 归档可校验、进度可观测 (Priority: P2)

运营者在归档前后各跑一次校验：逐批对比行数与抽样内容，确认"搬走的每一行都还在历史层、主库删的每一行都已被校验覆盖"。任何时候都能查看归档进度（哪些时间片已完成、当前水位在哪）。

**Why this priority**: 涉及从主库删除数据（不可逆动作），必须"先校验后删除、只报告不自动改账"的平台风格兜底；但它是 US1 的保障机制而非独立价值，排 P2。

**Independent Test**: 归档一批数据后执行校验命令，输出批次清单（时间范围/行数/校验状态）；人为制造一处不一致，校验能定位到具体批次并告警。

**Acceptance Scenarios**:

1. **Given** 一批数据已归档且校验通过，**When** 查看归档状态，**Then** 显示该批次时间范围、行数、校验通过标记与时间戳。
2. **Given** 校验发现某批次历史层行数与账目不符，**When** 校验运行，**Then** 报告该批次为不一致并阻止该批次的主库删除动作（若尚未删除）。

---

### Edge Cases

- 归档水位边界上的"活数据"：K 线表里最近一根 bar 仍在被更新（未闭合），归档切片必须只处理早于安全水位且已闭合的数据，不碰正在写入的行。
- 公共数据与租户数据混布：爆仓事件与 K 线是全平台公共市场数据（无租户维度），信号与订单是租户数据——历史层的隔离策略必须按数据类型区分，不能一刀切。
- 查询范围跨度极大（如整年分钟级 K 线）：单次查询返回行数可能巨大，需要上限与分页约定，防止一次查询拖垮服务。
- 历史层写入的金额/数量精度：主库以字符串精度语义存储，归档与回读全程不得引入浮点精度损失（constitution 原则 II 的跨存储延伸）。
- 时钟：所有归档水位、批次时间范围、查询边界统一 UTC。
- 归档服务首次接入时主库已有海量存量数据：首次归档是大批量搬迁，需要分批限速，避免一次性 IO 打满主库。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持对四类时序数据执行归档：K 线（kline_bars）、AI 信号（signals）、策略订单（strategy_orders）、大户爆仓事件（liquidation_events）。
- **FR-002**: 系统 MUST 按保留期划分冷热：早于保留水位的已闭合数据归入历史层，保留期内数据留在主库；保留期可按数据类型配置。
- **FR-003**: 归档执行 MUST 保证业务零感知：归档期间热链路（行情接入、聚合、策略调度、下单、信号、计费）的读写不被阻塞、不失败。
- **FR-004**: 归档 MUST 幂等且可续跑：同一批数据重复归档不产生重复行；批次中断后重新执行从断点继续，不丢不重。
- **FR-005**: 系统 MUST 提供**先校验后删除**的安全顺序：每批数据先在历史层完成落库与校验（行数 + 抽样内容一致），校验通过才允许移除主库对应行；未通过校验的批次禁止删除。
- **FR-006**: 系统 MUST 提供统一历史查询入口：调用方按（数据类型、时间范围、交易对、可选租户范围）查询，系统自动路由冷热两层、合并为完整有序结果，调用方无需感知数据所在层。
- **FR-007**: 历史查询 MUST 区分数据可见性域：租户数据（signals、strategy_orders）强制行级租户隔离；公共市场数据（kline_bars、liquidation_events）按平台公共数据处理，不允许任何租户越权读取他人租户数据。
- **FR-008**: 历史层 MUST 作为旁路依赖存在：其不可用时，主库热链路全部功能不受影响，历史查询返回明确的降级错误而非连锁失败。
- **FR-009**: 系统 MUST 提供归档状态查询能力：按数据类型展示已完成批次（时间范围、行数、校验状态）、当前归档水位、待归档量。
- **FR-010**: 归档全链路 MUST 保持金额/数量字段的字符串精度语义，历史层写入与回读不引入浮点精度损失；时间统一 UTC。
- **FR-011**: 历史查询 MUST 支持大范围查询的安全上限（单次返回行数上限与分页），超限时明确提示而非静默截断。
- **FR-012**: 首次归档 MUST 支持分批限速执行，避免存量大批量搬迁打满主库 IO 影响线上服务。

### Key Entities *(include if feature involves data)*

- **归档批次（Archive Batch）**：一次搬迁的原子单元——数据类型、时间范围（UTC）、行数账目、校验状态（待校验/通过/不一致）、完成时间戳；幂等续跑与"先校验后删除"都以此为粒度。
- **归档水位（Archive Watermark）**：每类数据各自记录的"已归档至某时间点"指针，推进与批次完成绑定；水位之外的早于保留期的数据为待归档。
- **历史查询请求/结果（Historical Query）**：数据类型、时间范围、交易对过滤、租户范围（仅租户数据）、分页游标；结果为完整有序时间序列。
- **保留策略（Retention Policy)**：每类数据各自的保留期配置与归档开关。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 归档后查询一年历史 K 线（分钟级）耗时低于 500ms，且结果完整有序。
- **SC-002**: 归档窗口内热链路零回归：与未开归档的基线相比，下单/信号/调度成功率无差异（0 失败增量），请求延迟无可感知退化。
- **SC-003**: 冷热合并查询与纯主库查询结果一致：跨越归档边界的查询行数与归档前基线完全一致（不丢行、不重行、顺序正确）。
- **SC-004**: 租户隔离零泄露：双租户历史数据归档后，跨租户历史查询测试 100% 拒绝泄露。
- **SC-005**: 归档幂等验证通过：同一批次重复执行归档行数不变；进程中断后续跑完成且账目对平。
- **SC-006**: 历史存储故障演练通过：断开历史存储期间热链路操作全部成功，恢复后归档续跑账目对平。
- **SC-007**: 主库瘦身可量化：首轮归档完成后，四类表超期行 100% 移出主库，主库备份耗时较归档前可测量下降。

## Assumptions

- 历史存储的具体选型与部署形态（自托管单节点起步、资源规格、备份策略）在 plan 阶段确定；spec 只约束行为契约。
- 主库到历史层的数据搬迁机制（批量搬迁 vs 双写切换）在 plan 阶段决策；spec 约束"业务零感知 + 幂等 + 先校验后删除"三条行为红线。
- 保留期默认值取 90 天（业界常见时序保留基线），按数据类型可配置；首次归档前由运营确认实际值。
- 已归档且校验通过的数据从主库移除；主库不长期保留已归档数据的影子副本（备份快照天然提供时间点恢复能力）。
- P10 回测引擎与 P7 DSL 回测预览是统一历史查询的首批下游消费者；本期先交付查询能力，下游接入属各自阶段范围。
- Reverb 广播历史数据、历史层上的聚合分析（如逐租户用量报表）不在本期范围。
